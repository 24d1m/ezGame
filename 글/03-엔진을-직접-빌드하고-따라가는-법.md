# 혼자 운영하는 서버가 엔진을 직접 빌드하고 따라가는 법

2026-11-15

EZ는 PocketMine-MP 포크인 Axolotl-PM 위에서 돈다. 원래 PocketMine 본가는 올해 여름에 보관(읽기 전용) 처리됐고,
베드락 최신 버전과 새 접속 방식(NetherNet)을 지원하는 건 Axolotl 같은 커뮤니티 갈래뿐이다. 팀이 작다.

그래서 엔진은 두 가지 이유로 신경이 쓰인다.

- 베드락은 몇 주마다 새 버전이 나온다. 엔진이 따라오기 전까지 새 버전 플레이어는 못 들어온다
- 렉을 잡다 보면 엔진 안쪽을 건드리고 싶어진다. 그런데 건드릴수록 업데이트를 따라가기가 어려워진다

이 글은 그 둘 사이에서 어떻게 균형을 잡았는지에 대한 기록이다.

## 시작은 리플렉션이었다

처음부터 엔진을 고칠 생각은 없었다. 렉을 잡다가 플러그인에 이런 코드가 생겼다.

- GC 기준값을 바꾸려고 `GarbageCollectorManager`의 private 속성을 리플렉션으로 덮어씀
- 접속용 패킷 캐시를 서버 시작 때 미리 만들려고 private 함수를 리플렉션으로 호출
- 경기장 월드의 빛 계산을 끄려고 청크의 "빛 계산 끝남" 표시를 비워서 엔진을 속임

셋 다 잘 돌았다. 문제는 엔진 업데이트로 이름 하나만 바뀌어도 **아무 말 없이** 효과가 사라진다는 점이었다.
렉이 다시 생기고 나서야 알게 된다.

그래서 필요한 함수 세 개를 엔진에 정식으로 넣기로 했다. 패치가 새 판에 안 붙으면 빌드가 멈추니, 적어도 조용히 깨지지는 않는다.

## 원칙 세 가지

엔진을 고치기 전에 원칙부터 정했다.

1. **패치는 작게.** 함수 하나 추가, 조건문 하나 추가 수준. 엔진 구조를 바꾸지 않는다
2. **플러그인은 패치가 없어도 돈다.** 함수가 있으면 쓰고, 없으면(공식 엔진) 예전 방식으로 돈다. 급하면 언제든 공식 판으로 돌아갈 수 있다
3. **플러그인이나 공개 함수로 되는 건 엔진에 넣지 않는다**

3번이 생각보다 많은 걸 걸러냈다. 아래에 따로 적었다.

## 공식 빌드와 똑같이 만들기

처음엔 소스를 받아 `composer install`을 하고 phar를 만들었다. 패치 없이 만든 판을 공식 phar와 비교해 보니 클래스맵과 플랫폼 검사 파일이 달랐다.
공식 릴리스 워크플로를 열어 보고 같은 옵션(`--no-dev --prefer-dist --ignore-platform-reqs`)과 같은 빌드 번호로 맞췄다.
그 뒤로 패치 없는 판과 공식 판의 차이는 JSON 압축 여부와 버전 표기뿐이다.

"내가 만든 엔진이 공식 엔진과 패치 말고는 같다"는 걸 확인할 수 있어야, 문제가 생겼을 때 패치를 의심할지 엔진을 의심할지 정할 수 있다.

## 새 판은 기계가 먼저 본다

패치를 들고 있으면 새 판이 나올 때마다 할 일이 생긴다. 이걸 사람이 챙기면 언젠가 늦는다. 그래서 자동으로 돌게 했다.

1. 1시간마다 GitHub 최신 릴리스를 본다
2. 새 판이면 공식 phar와 `build_info.json`(빌드 번호, PHP 판, 마크 판)을 받는다
3. 패치를 붙여 빌드하고, 우리 플러그인 정적 검사와 불러오기 검사를 새 엔진으로 돌린다
4. 통과하고 시험 서버가 꺼져 있으면 시험 서버에 올려 둔다
5. 실서버에 접속자가 없으면 시험 서버를 잠깐 켜서 부하 테스트(봇으로 6판, 2분)를 돌리고 끈다
6. 결과를 운영 디스코드로 보낸다. 준비됨 / 패치가 안 붙음 / 빌드·검사 실패 중 하나, PHP 판이 바뀌었으면 그 경고까지

실서버에 올리는 것만 사람이 한다. 알림을 보고, 휴대폰으로 시험 서버에 들어가 보고, 그다음에 올린다.

5번에서 "실서버에 접속자가 없을 때만"을 넣은 이유는, 시험 서버가 실서버와 같은 VPS에 있기 때문이다.
2코어짜리 서버에서 부하 테스트를 돌리면 실서버 플레이어가 렉을 느낀다. 처음 시험할 때 마침 실서버에 한 명이 있었고, 스크립트가 알아서 건너뛰었다.

지금 판으로 일부러 돌려 보니 빌드에 14초, 부하 테스트까지 5분쯤 걸렸다. TPS는 평균 20.0, 최저 20.0이었다.

## 하지 않기로 한 것들

패치 세 개를 넣은 뒤 후보를 더 적어 보니 아홉 개가 나왔다. 막상 하나씩 엔진 코드를 열어 보니 대부분 엔진을 고칠 필요가 없었다.

| 후보 | 엔진을 고치지 않은 이유 |
|---|---|
| 경기장 전용 메모리 월드 | 경기장은 이미 메모리 디스크(/dev/shm)에 만든다. 디스크를 기다리는 시간이 없다 |
| 엔진 전체에 거리별 움직임 패킷 줄이기 | 로비의 고래, 열기구, 동물, 펫은 엔진 엔티티가 아니라 플러그인이 직접 그린다. 엔진 패치가 닿지 않는다 |
| 블록 여러 개 한꺼번에 바꾸기 | 깜빡임이 문제였던 재난은 플러그인에서 이미 묶어 보낸다 |
| 비동기 작업에 이름표 붙이기 | 엔진 타이밍에 이미 작업 이름이 찍힌다 |
| 경기장 땅 미리 보내기 | 경기장 이동은 이미 규칙 안내 화면이 가린 뒤에 한다 |
| IP별 접속 · 로그인 빈도 제한 | 만들긴 했다. 다만 엔진이 아니라 TCP 중계기(직접 만든 것)와 플러그인에서, 엔진 공개 함수 `Network::blockAddress`를 써서 |
| 접속 단계별 시간 | 이것도 만들었다. 접속 때 오가는 패킷만 보면 돼서 플러그인으로 |

목록을 처음 만들 때 엔진 코드를 끝까지 보지 않고 "이런 게 있으면 좋겠다"로 적은 탓이다.
아홉 개 중 엔진 패치가 된 건 하나(틱을 단계별로 나눠 재기)뿐이고, 셋은 플러그인과 중계기로 만들었고, 다섯은 필요 없었다. 엔진에 들어간 패치는 모두 네 개다.

| 패치 | 하는 일 |
|---|---|
| 001 | GC 기준값을 바꾸는 공개 함수 |
| 002 | 크리에이티브 목록 캐시를 미리 만드는 공개 함수 |
| 003 | 월드마다 서버 빛 계산을 끄는 설정 |
| 005 | 바로 앞 틱이 단계별로(플러그인 작업, 비동기 완료, 월드, 네트워크, GC) 몇 ms였는지 늘 잰다 |

005는 렉 기록용이다. 전에는 측정 명령을 켜 둔 때만 원인을 알 수 있었다.
지금은 느린 틱이 나면 로그 한 줄에 단계별 시간이 같이 남는다. 틱마다 `hrtime()`을 일곱 번 부르는 정도라 부담은 거의 없다.

## 서버를 빠르게 해도 화면은 안 빨라졌다

같은 날 접속 시간도 단계별로 재기 시작했다. 접속할 때 오가는 패킷만 보면 되니 엔진 패치 없이 플러그인으로 된다.
갤럭시 S26에서 리소스팩을 이미 가진 상태로 들어가면 이렇다.

```
총 3.9초 · 로그인 확인 0.2 · 서버 준비 0.3 · 땅 보내기 1.6 · 기기 그리기 1.8
```

땅 보내기 1.6초가 눈에 띄었다. 그래서 엔진 설정 두 개를 바꿔 봤다. 틱마다 보내는 청크 수를 4개에서 8개로, 화면을 띄우기 전에 보내는 반지름을 4에서 3으로.

| | 땅 보내기 | 기기 그리기 | 총 |
|---|---|---|---|
| 원래 설정 | 1.6 | 1.8 | 3.9초 |
| 바꾼 설정 (두 번째 접속) | 0.5 | 2.6 | 3.5초 |

땅 보내기는 0.5초로 줄었다. 그런데 그만큼 기기 그리기가 늘었다. 서버가 빨리 보내도 휴대폰이 받아서 처리하는 속도는 정해져 있었다.
병목은 서버가 아니라 휴대폰이었다. 설정은 되돌렸다. 바꿔 봐야 접속 순간 서버 일만 몰린다.

처음 오는 사람은 여기에 리소스팩(4개, 약 21MB)을 받는 시간이 더해진다. 빠른 회선에서 4.7초, 총 8.2초였다.
느린 회선이면 30초쯤 걸릴 수 있다. 일단은 그 정도면 괜찮다고 보고, 오픈 뒤 실제 숫자를 보기로 했다.

## 정리

- 엔진을 고치는 건 어렵지 않다. 고친 엔진을 **계속 따라가는 것**이 어렵다
- 그래서 패치는 작게, 적게, 없어도 돌게. 새 판은 사람보다 기계가 먼저 보게
- 고치기 전에 코드를 끝까지 읽으면 고칠 게 줄어든다. 이번엔 후보 아홉 개 중 엔진까지 간 건 하나였다
- 빠르게 만든 게 진짜로 빨라졌는지는 끝에서 재야 안다. 서버 숫자만 보면 속는다
