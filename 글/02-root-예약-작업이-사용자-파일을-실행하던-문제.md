# root 예약 작업이 게임 서버 사용자의 파일을 실행하고 있었다

2026-11-09 발견, 같은 날 고침

## 어쩌다 봤나

서버 밖 백업 업로더를 붙이던 새벽이었다. 업로더를 어떤 사용자 권한으로 돌릴지 정하려고, 지금 서버에서 root로 도는 게 뭐가 있는지부터 훑었다.
cron 목록을 보다가 관리 상황판을 만드는 예약 작업 두 줄에서 멈췄다.

```
* * * * *      root  <게임 폴더>/bin/php7/bin/php <게임 폴더>/tools/.../admin_status.php ...
2-59/5 * * * * root  <게임 폴더>/bin/php7/bin/php <게임 폴더>/tools/.../admin_data.php ...
```

root가 1분마다 PHP 스크립트를 돌리는데, 실행 파일도 스크립트도 게임 폴더 안에 있었다.
게임 폴더는 통째로 게임 서버 사용자 소유다. 게임 서버가 월드, 설정, 로그를 써야 해서 설치할 때 `chown -R`을 해 뒀다.

즉 **게임 서버 사용자가 고칠 수 있는 파일을 root가 실행하고 있었다.**
게임 서버 플러그인이나 PHP 쪽 취약점으로 그 사용자 권한을 얻으면, 스크립트에 한 줄 넣고 1분만 기다리면 root가 된다.
뚫린 흔적이 있었던 건 아니다. 게임 서버가 먼저 뚫려야 쓸 수 있는 2단계 길이다. 그래도 서버 전체가 넘어가는 길이라 바로 고치기로 했다.

## 스크립트만 볼 게 아니었다

처음엔 스크립트 두 개를 root 소유로 바꾸면 끝이라고 생각했다. 실행되는 것들을 끝까지 따라가 보니 그렇지 않았다.

| 무엇 | 소유 |
|---|---|
| PHP 스크립트 2개 | 게임 서버 사용자 |
| PHP 실행 파일 | 게임 서버 사용자 |
| php.ini (`zend_extension`, `extension_dir` 포함) | 게임 서버 사용자 |
| PHP가 불러오는 공유 라이브러리 (`ldd`) | 게임 폴더를 가리키는 줄 13개 |

스크립트를 root 소유로 바꿔도 php.ini에 `auto_prepend_file=` 한 줄이면 똑같이 뚫린다.
libssl 같은 라이브러리 하나를 바꿔치기해도 된다. 인터프리터, 설정 파일, 라이브러리까지 전부 같은 사용자 손에 있었다.

이 문제를 확인하는 순서를 정리하면 이렇다.

1. root로 도는 것 목록: cron, systemd 서비스, sudoers
2. 그것이 실행하거나 읽는 파일의 소유자
3. 인터프리터, 그 설정 파일, 공유 라이브러리까지

3번을 빼먹기 쉽다. 나도 처음엔 빼먹었다.

## 왜 생겼나

설치 스크립트는 게임 서버가 쓸 수 있게 게임 폴더 전체를 게임 서버 사용자에게 넘겼다.
상황판은 fail2ban 차단 숫자를 읽어야 해서 root로 돌렸다.
따로 보면 둘 다 그럴듯한 결정인데, 둘이 만나면서 틈이 생겼다. CWE-732(중요한 자원에 잘못된 권한) 계열의 흔한 꼴이다.

## 고친 방법

원칙을 하나로 정했다. **root는 root 소유 파일만 실행한다. 게임 서버 사용자 파일은 그 사용자 권한으로만 돈다.**

상황판 작업을 둘로 쪼갰다.

- **root 쪽**: 정말 root가 필요한 숫자(fail2ban 차단 수 같은 것)만 모은다
  - 실행은 시스템 PHP로 한다 (apt로 깔린 root 소유)
  - 스크립트도 root 전용 폴더에 둔 root 소유 사본이다
  - 결과는 JSON 파일 하나로 내놓고, 게임 서버 사용자는 그 파일을 읽기만 한다
- **게임 서버 사용자 쪽**: 나머지 상황판 계산 전부. 원래 PHP를 그대로 쓰되 root가 아닌 그 사용자 권한으로 돈다

시스템 PHP에는 json과 posix 확장만 있었다. 그래서 root 쪽 스크립트는 yaml, sqlite 없이 json만 쓰게 나눴다.

배포 순서도 신경 썼다. 코드를 먼저 올리고 cron을 나중에 바꾸면, 그 사이에 상황판이 깨질 수 있다.
그래서 새 코드는 root 쪽 결과 파일이 없을 때(아직 옛 cron이 돌 때)만 예전처럼 직접 세게 해 뒀다. 덕분에 순서가 섞여도 상황판이 멈추지 않았다.
설치 스크립트 마지막에는 "root가 게임 폴더 안의 무언가를 실행하는 예약 작업이 남았는지"를 스스로 검사하는 단계를 넣었다.

고친 뒤 확인한 것:

- root cron 중 게임 폴더를 건드리는 줄 0개
- 게임 서버 관련 서비스 3개 모두 게임 서버 사용자로 실행
- 첫 실행(11:54)에서 상황판 숫자가 정상으로 들어옴

## 이틀 뒤, 같은 문제의 다른 얼굴

11월 11일에 다시 점검하다가 같은 꼴을 하나 더 찾았다. 이번엔 예약 작업이 아니라 **사람이 직접 하는 설치**였다.

관리 패널이나 서비스를 다시 설치할 때 root로 설치 스크립트를 돌리는데, 그 스크립트가 게임 폴더 안에 있었다.
게임 서버가 뚫린 상태에서 내가 아무것도 모르고 설치를 다시 하면 그때 root가 된다.

고친 방법은 같은 원칙이다.

- 설치할 때마다 원본을 root 전용 폴더에 새로 풀어서 거기서만 실행한다
- 그 폴더와 위쪽 폴더들이 root만 쓸 수 있는지, 해시가 맞는지, 심볼릭 링크가 섞였는지 먼저 확인한다. 하나라도 이상하면 멈춘다
- 설치 스크립트를 게임 폴더 안에서 root로 실행하면 스스로 멈추게 했다

하나 더 있었다. 배포 스크립트가 root로 게임 폴더 안에서 `chmod +x`와 `cp -a`를 하고 있었다.
`chmod`는 심볼릭 링크를 따라간다. 게임 서버 사용자가 미리 링크를 심어 두면 엉뚱한 파일의 권한이 바뀐다.
`find -type f`로 일반 파일만 골라 권한을 주고, 복사는 `cp -a --remove-destination`으로 있던 링크를 지운 뒤 새로 쓰게 바꿨다.

## 배운 것

- "root로 돈다"를 봤으면 실행 파일 하나가 아니라 **그 실행에 딸려 오는 모든 것**의 소유자를 봐야 한다. 인터프리터, 설정, 라이브러리, 그리고 그걸 부르는 사람의 습관까지
- 따로 보면 맞는 결정 두 개가 합쳐져서 구멍이 된다. 권한을 넘기는 결정을 할 때는 그 폴더를 누가 실행하는지도 같이 적어 두는 게 좋겠다
- 고칠 때 바로 막는 것보다 원칙을 한 줄로 정하는 게 오래 간다. 이 뒤로 root가 하는 일을 새로 만들 때마다 이 한 줄에 맞는지부터 본다
